## Pin labels (`vioarm boards --pins`)

HIL wiring needs human pin names, not SVD windows:

```sh
vioarm boards --pins stm32f103   # one board
vioarm boards --pins all         # all 13 tables
```

Tables live in `vioarm-core/src/pins.rs` (`pin_labels`, `PIN_BOARDS`):
`stm32f103`, `stm32f107`, `stm32f407`, `stm32f401`, `stm32f072`,
`stm32f030`, `stm32f303xe`, `stm32l476`, `stm32g474xx`, `stm32h743`,
`stm32u575`, `stm32wba55`, `stm32l552`. Each row is `PIN: FUNCTION` in
the default alternate-function mapping firmware actually uses
(`PA9: USART1_TX`, `PC13: GPIO_O`, …); the full AF matrix is explicitly
out of scope. Unknown boards error with the valid list. `vioarm docs
boards` points here.

## Phase 0 audit: per-board peripheral tiers (`boards-roadmap.md`)

Generated by `cargo run -p vioarm-core --example board_audit`: each
family board is built, its SVD table walked, and every bus window
classified by the mounted device — `behavioral` (hand-written device,
T2-or-better) vs `latch` (pure `NoBehavior` register file, T1).
System-block windows (`0xE000_0000+`: NVIC/SCB/SysTick) are `core`
modeled in the CPU, not on the bus. Variants (`stm32f030c6`, …)
delegate to their family constructor, so the 21 families below are the
complete behavioral picture (1,046 bus windows: **454 behavioral**,
592 latch, plus 60 core-owned).

Caveats: `behavioral` includes handshake-only stubs (`LTDC`/`DMA2D`/
`BDMA`/`MDMA`/`SAI4`/`DFSDM`/`HRTIM` on `h743` and friends — IRQs
latch, data paths descoped); promoting those is Phase B work. The
`f0x*` generics are intentionally minimal SVD donor tables, not real
boards — the real F0 boards are `f030/f031/f042/f072/f091`.
